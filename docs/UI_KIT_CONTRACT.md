# UI Kit contract

`/ui-kit` — жива бібліотека authenticated workspace QuickTeam. Це не окремий
демо-дизайн: preview рендерять ті самі shared-компоненти та semantic CSS
contracts, що й робочі екрани.

## Межі каталогу

- Сканування починається з `src/app/(app)` і рекурсивно проходить лише reachable
  local imports.
- Login, onboarding та інші непідключені до authenticated workspace екрани не
  визначають повноту каталогу.
- Невикористані legacy-файли під `src/components/ui` не показуються в
  `/ui-kit` і не вважаються частиною живого каталогу.
- Брендування залишається тільки у sidebar та його contrast-dependent
  дочірніх елементах.

## Кольори

Кожен колір у продукті береться з токена в `@theme` (`src/app/globals.css`), а
не з сирого hex і не з палітри Tailwind.

- Бренд: `ink`, `ink-hover`, `canvas`, `surface`, `line`, `muted`, `faint`.
  Три ваги сірого для тексту, і четвертої немає.
- Статус: `success`, `warning`, `danger`, `info` — кожен у трьох ролях.
  `text-danger` — чорнило (єдина роль, що зобовʼязана тримати AA на білому);
  `bg-danger-solid` — заливка (крапка, смуга, індикатор); `bg-danger-soft` —
  підкладка під рядок того чорнила. Одне значення не може бути всіма трьома —
  саме тому кожен екран доти вигадував відсутнє.
- Графіки: `chart-1..3`, `chart-track`, `chart-context`, `chart-grid`.
- Сайдбар брендується організацією, тому все всередині нього читає
  `--sb-bg`/`--sb-text`/`--sb-muted`/`--sb-hover`/`--sb-active`, а не бренд-токени.
  `Counter appearance="sidebar"` — той самий принцип для лічильника.

Сирий hex лишається легальним рівно там, де значення не є оформленням: палітра
на вибір користувачу, колір статусу/типу/пріоритету з бази, `canvas`-API,
згенерований QR, і вбудований документ для друку, який не бачить CSS продукту.

## Кандидати

[`src/components/ui/CANDIDATES.md`](../src/components/ui/CANDIDATES.md) —
місцеві компоненти, які під час візуального проходу виявилися справді
унікальними, і відкриті питання про них. Це список рішень, не склад коду:
компонент, якого продукт не використовує, у `src/components/ui` не живе.

## Правила для кожної майбутньої UI-зміни

1. Повторюваний visual pattern живе в `src/components/ui`.
2. Новий shared-компонент у тій самій зміні:
   - експортується з `src/components/ui/index.js`;
   - використовується authenticated workspace;
   - має живий preview у `/ui-kit`.
   Invariant: A new shared component is exported, used by the authenticated
   workspace, and rendered in `/ui-kit` in the same change.
3. Geometry і typography задаються semantic contract у `globals.css`, а не
   анонімним `h-[Npx]`, `text-[Npx]` чи radius override поверх shared API.
4. Контекстна різниця отримує named prop або attribute: `size`, `context`,
   `density`, `preset`, `composition`, `data-ui-*`.
5. `Label` відповідає за typography/required state; відступ до control задає
   `FormGroup` або layout.
6. Форми у side sheet/modal використовують `Dialog`. Media viewers, responsive
   panes і navigation overlays мають окремі чесно названі оболонки.
7. Pills/badges/counters належать semantic family (`Pill`, `Counter`,
   `StatusPill`, `TypeBadge`, `Tag`), але не змішують свою data semantics.
8. Neutral compact actions використовують `IconAction`; спеціальні media,
   editor чи branded actions мають named appearance.
9. Повторювані Card/Surface patterns використовують semantic surface presets.
   Справді одноразовий structural container позначається
   `data-ui-surface="local"` і залишається видимим в audit як reviewed exception.
10. Локальний компонент не може маскуватися назвою іншого UI Kit компонента:
    справжній повтор canonicalize, контекстний компонент отримує точну назву.

## Затверджені fidelity-рішення

1. Єдине джерело geometry та typography — Semantic CSS contract.
2. Form labels — один `Label`, gap задає layout.
3. Side sheets — `Dialog` для форм, viewers окремо.
4. Pills, badges та counters — semantic family.
5. Compact neutral icon actions — shared `IconAction`.
6. Виняткові висоти controls — named composition presets.
7. Компоненти-двійники — canonicalize або чесно перейменувати.
8. Card/Surface/local boundary — shared semantic surfaces із явними local
   exceptions.
9. Typography — named contexts.
10. Повнота каталогу — тільки authenticated workspace.

Попередні десять product-рішень (CTA dark/red, scale 24/18, sm/md/lg controls,
shared chat core, task/calendar chrome, surface/filter presets, `StatusPill`,
`EmptyState` contexts і extraction лише повторюваних controls) закріплені в
`tests/kit-usage.test.mjs`; екрана `DecisionLab` більше немає.

## Затверджені follow-up рішення

1. Приховані Kanban-колонки мають context preset: у проєкті вони повністю
   приховані, у cross-project Kanban їхні задачі збираються у lane «Приховані».
2. `TaskListView` отримує `hiddenStatusIds` і збирає задачі прихованих статусів
   у явну секцію «Приховані». Це однакова shared-поведінка обох списків; у
   проєкті після зміни видимості задачі прихованих колонок серверно переходять
   у Беклог, тому секція з’являється лише коли в ній справді є задачі.
3. Створення з Kanban є context-aware: у проєкті лишається швидкий inline add,
   а cross-project view відкриває повну форму з вибором проєкту.
4. `IssueCard` і `TaskRow` показують назву проєкту лише з явним
   `showProjectName` у cross-project views.
5. Епік не є спеціальним рівнем ієрархії. Нові задачі використовують типи
   `Фіча`, `Задача`, `Баг`; наявні Епіки лишаються видимими як legacy-тип до
   окремої перевіреної міграції, але нові Епіки не створюються.
6. Справжня підзадача — повноцінний issue з `parentIssueId`, власним ключем,
   статусом, виконавцями, часом і оцінкою. Глибина — один рівень. Батьківська
   задача показує прогрес дітей і не закривається, доки відкриті діти або
   блокуючі залежності. Lightweight-кроки живуть лише як Markdown-checkbox в
   описі; legacy `subtasks[]` можна явно перенести в опис.
7. Логічні зв’язки не створюють ієрархію: доступні `Залежить від`, `Блокує`,
   `Пов’язана з`, `Дублює`. Directional `blocks` зберігається один раз як
   `source blocks target`; UI виводить правильну перспективу з обох боків.

Екранів `FidelitySurvey` і `FidelityFollowUpSurvey` більше немає — рішення вище
є продуктовою поведінкою і закріплені в `tests/kit-usage.test.mjs`.

## Одна сторінка

`/ui-kit` — єдина довідкова сторінка, і вона каталог компонентів. Були ще дві:
`/ui-audit` зі 145 нативними контролями і `/ui-diff` із дублікатами патернів.
Обидві — звіти в одязі каталогу, і поки їх було три, жодна не відповідала на
питання «з чого мені будувати?». Звіти нікуди не поділись: вони лишились
generated JSON + падаючим тестом. Звіт не стає розділом каталогу.

## Лейаути

Екрани, які «виглядають інакше», — це не виняток із кіту, а іменований контекст
у ньому. Settings, Team і Chat усі рендерять `SidebarLayout`; жолоб, ширина
рейки й відступ 56px під фіксованим хедером живуть у `CONTEXTS` і більше ніде.

| Контекст | Чим відрізняється |
| --- | --- |
| `settings` | Володіє всією висотою вікна; лейаут малює білу панель контенту сам. |
| `team` | Під фіксованим хедером; права панель — `Surface preset="panel"`, тому сторінка малює її сама. |
| `chat` | Під фіксованим хедером; чат подає дві панелі поруч — розмову й гілку. |

До цього тільки Settings викликав компонент, а Chat і Team переписували той
самий каркас руками — звідки й розійшлись: один і той самий проміжок 12px був
написаний як `gap-3` в одному місці й `gap: '12px'` в іншому, а обидва екрани
під хедером пам'ятали про 56px кожен окремо.

## Автоматичні перевірки

Порядок має значення: кожна наступна читає вихід попередньої.

- `npm run kit:colors` — кожен колір, що є оформленням, приходить із токена.
  Сирий hex і палітра Tailwind у продуктових файлах — нуль; колір, що є даними
  (палітра на вибір, колір статусу з бази, `canvas`, QR, документ для друку),
  перелічений у `DATA_COLORS` разом із причиною.
- `npm run kit:scan` — inventory shared UI, реальні usages, маршрути і live previews.
- `npm run kit:states` — які стани має кожен компонент; читає inventory зі `scan`.
- `npm run kit:props` — API кожного компонента: пропси, дефолти, оголошені
  значення й опис із JSDoc.
- `npm run kit:a11y` — доступність: контроли без імені, `img` без `alt`,
  ручний tab-порядок, `onClick` на `div`, контраст тихих текстових токенів;
  динамічні імена окремо виносить у чергу runtime-перевірки.
Чи доходить `data-ui-*` оголошення до екрана, вирішує не скрипт, а браузер —
див. «Шари вирішують, а не специфічність».
- `npm run kit:drift` — там, де продукт **таки бере** компонент із кіту: чи
  рендерить він його значеннями, які кіт оголошує, і чи каталог їх показує.
- `npm run kit:audit` — native controls, labels, overlays, pills, surfaces,
  icon actions, typography contexts, chrome overrides і name collisions.
- `npm run test:unit` — перевіряє актуальність усіх шести generated reports та
  забороняє новий unreviewed drift.

Generated reports (усі шість поруч, у `src/app/ui-kit/`):

- `kit-usage.generated.json`
- `kit-states.generated.json`
- `kit-props.generated.json`
- `kit-drift.generated.json`
- `a11y-audit.generated.json`
- `fidelity-audit.generated.json`

## Таблиця пропів

«Які пропси в цього компонента?» відповідалося тільки відкриттям файлу. Каталог
показував, як компонент виглядає і де він живе, і мовчав про те, як його
викликати — тому кожен новий виклик писався копіюванням сусіднього, разом із
дефолтами, які вже могли бути не тими.

Панель компонента (кнопка з пін-іконкою на превʼю) відкриває таблицю, і вся
вона витягнута з коду `scripts/kit-props.mjs`:

- **пропси** — власні деструктуровані параметри компонента;
- **дефолт** — вихідний текст значення, тож `size = 'lg'` читається так само, як
  у сигнатурі;
- **оголошені значення** — із того самого маніфесту варіантів, тому таблиця й
  «Матриця варіантів» не можуть розійтися;
- **опис** — JSDoc (`@param {type} props.name - текст`) або трейлінг-коментар
  `// …` біля пропа, який у цьому коді писали й до того, як його хтось читав.

Два контрактні нулі, обидва тримає `tests/kit-props.test.mjs`: компонентів без
summary — 0, пропів без опису — 0.

Три помилки видобування, які давали правдоподібний нуль замість падіння, і
через це закриті регресійними перевірками:

1. **Док-коментар стоїть над інструкцією, не над функцією.** У
   `export default function X` вузол функції починається на `function`, тож
   проміжок до коментаря завжди містить `export default` — і всі 73 summary
   поверталися порожніми.
2. **Половина кіту лежить у CRLF.** `.` не матчить `\r`, тому патерн із якорем
   `$` не знаходив трейлінг-коментарів саме в цих файлах: `Button` не
   документував жодного пропа, а сусідній `ToggleSwitch` — усі.
3. **Тип із фігурними дужками.** `{{label: string}[]}` і `{(e) => void}`
   обривали `\{([^}]*)\}` на першій внутрішній дужці, і проп зникав цілком.

## Одна секція — один файл

Каталог більше не один файл на 3300 рядків. `src/app/ui-kit/page.js` — це
оболонка: навігація, `SECTION_MAP` і більше нічого. Кожна секція живе в
`src/app/ui-kit/sections/<section-id>.jsx`, і **ім'я файлу дорівнює id секції в
навігації** — саме це дозволяє будь-якому інструменту знайти джерело секції, не
розбираючи сторінку.

Що це змінює по суті: превʼю зараховувалось, лише якщо компонент рендериться
безпосередньо в тілі функції секції. Не тому, що так правильно, а тому, що три
інструменти читали «тіло секції» як текст від `function XSection(` до наступного
`function`. Винесеш блок у хелпер — покриття мовчки падало. Тепер секція
зараховується цілим файлом, тож хелпери всередині неї теж рахуються.

`preview.jsx` (`PreviewBlock`, `TokenChip`, `StatusDot`) і `demo-data.js` —
спільний реквізит, і покриття вони не дають: `PreviewBlock` не рендерить жодного
компонента кіту, а хелпер не повинен мати права зробити секцію «покритою».

Знання про цю розкладку живе в одному місці — `scripts/ui-kit-showcase.mjs`.
Раніше його копії лежали в двох скриптах і чотирьох тестах.

## Знімки секцій

Три звіти вище відповідають на питання «чи бере продукт компонент із кіту і
чи передає йому оголошені значення». Жоден із них не бачить, що контрол
з'їхав на чотири пікселі, втратив рамку або що зникла ціла картка.

`npm run test:visual` фотографує кожну секцію `/ui-kit` — по одному знімку на
секцію, у стані спокою — і порівнює з бейзлайном у `tests/visual/__screenshots__`.
Падіння віддає трійку expected/actual/diff артефактом GitHub Actions. Виняток
один: «Матриця станів» знімається двічі, другий раз — із примусовими
псевдокласами (`states-forced.png`, див. нижче).

Три рішення, без яких це не працює:

1. **Бейзлайни пише лише CI.** Растеризація шрифтів на Linux не збігається з
   Windows чи macOS, тому знімок із машини розробника не зійшовся б ніколи.
   Локально та сама команда — димовий тест: проходить усі секції й падає на
   помилці консолі, але пікселі не порівнює і бейзлайн не створює.
2. **Прийняти зміну — це запустити workflow `UI Kit screenshots` з
   `update_baselines`.** Він перезнімає всі секції й комітить нові PNG. Різниця
   в PR тоді видима як діф картинок, а не як зелений тест.
3. **Знімається `next dev`, а не збірка.** Обхід у `src/proxy.js` пускає
   `/ui-kit` без сесії лише в development; продакшн-збірка відправила б тест на
   `/login`.

Дві пастки середовища, які коштували години: сторінку треба відкривати як
`localhost`, бо на `127.0.0.1` Next 16 вважає запит іншим dev-origin і не
піднімає клієнтський рантайм — сторінка рендериться, але ігнорує будь-який клік
без жодної помилки в консолі. І клік по навігації треба повторювати, доки
секція не перемкнеться: до гідрації він не лишає сліду.

## Матриця станів

Знімок стану спокою відповідає на питання «як це виглядає». Він ніколи не
відповідає на «як це виглядає, коли недоступне, зайняте, помилкове або коли в
нього поклали вчетверо більше тексту, ніж малювали» — а ламається UI саме там.

`/ui-kit` → «Матриця станів» показує шість станів: `hover`, `focus`,
`disabled`, `loading`, `error` і довгий текст. Перелік станів компонента —
не список, який хтось веде, а висновок із реалізації (`scripts/kit-states.mjs`):

| Стан | Звідки береться |
| --- | --- |
| `disabled` / `loading` / `error` | Компонент деструктурує проп, **або** розливає rest на нативний контрол, який володіє `disabled` сам (`Input`, `Textarea` не називають його жодного разу). |
| `hover` | `hover:` утиліта в компоненті, або `:hover` правило в `globals.css` на клас, який компонент рендерить. |
| `focus` | `focus…:` утиліта, або нативно фокусований елемент — `globals.css` дає всім кнопкам, посиланням і полям один ring в одному місці. |
| довгий текст | Компонент бере текстовий проп (`children`, `label`, `title`, `placeholder`…) або форвардить `value` у нативне поле. |

Наслідок той самий, що й у матриці варіантів: компонент **не може отримати
стан, якого каталог не показує**. `tests/kit-states.test.mjs` тримає це нулем.

Два стани з шести — псевдокласи. Власного DOM у них немає: одночасно навести
курсор на тридцять контролів неможливо, отже їх не рендерять, а провокують.
Клітинки несуть `data-kit-state`, а `tests/visual/ui-kit.spec.mjs` вмикає на
їхньому піддереві справжні `:hover` і `:focus-visible` через CDP
(`CSS.forcePseudoState`) і робить другий знімок — `states-forced.png`.

Чому саме так, а не статичний клас із тими ж кольорами: статичний клас — це
друга копія стилів компонента, яка живе в каталозі й вільна розійтися з
оригіналом. Примусовий псевдоклас змушує браузер зіставити **власні** правила
компонента, тому каталог не повторює про нього жодного рішення. Форс іде на все
піддерево клітинки, бо `group-hover:` читає курсор на предку, а
`peer-focus-visible:` — на сусідові.

## Доступність

Знімок не бачить, що в контрола немає імені, що іконкова кнопка представляється
як «кнопка, кнопка, кнопка», або що підпис над полем ні до чого не прикріплений.
Нічого з цього не видно на картинці — і все це різниця між екраном, яким можна
користуватися з клавіатури й зі скрінрідером, і екраном, яким не можна.

`npm run kit:a11y` тримає пʼять нулів по всьому автентифікованому воркспейсу
**і** по кіту:

| Категорія | Що означає |
| --- | --- |
| `namelessControls` | Іконковий контрол, якому нічого сказати про себе. |
| `imagesWithoutAlt` | `<img>` без `alt` — навіть без порожнього. |
| `positiveTabIndex` | Tab-порядок, написаний руками. Він завжди розходиться з візуальним і губить те, про що забули. |
| `fakeButtons` | `onClick` на `div`/`span`: не фокусується, недосяжний з клавіатури, мовчить для скрінрідера. |
| `contrastFailures` | Тихі бренд-сірі стали невидимими або злилися одне з одним; текстові токени дефолтного сайдбара нижче AA. `--color-muted` / `--color-faint` — свідоме рішення бренду і нижчі за WCAG AA для основного тексту; гейт стежить лише за тим, щоб вони не поїхали в невидимість і щоб `faint` лишався тихішим за `muted`. Сайдбарні теми обчислюються, а не обираються, тому там залишається повний поріг 4.5:1. |

`runtimeNameVerification` не є шостим нулем. Це чесна черга для контролів із
`aria-label={...}` / `title={...}`: сам JSX доводить, що джерело імені є, але
лише браузер може довести, що фактичне значення не порожнє. Динамічний атрибут
ніколи не зараховується як статично гарантоване імʼя.

Правила навмисно вузькі. Автоматична a11y-перевірка повна тестів, які загалом
праві й тут помиляються, тому цей файл повідомляє лише те, що можна вирішити з
коду без вгадування — інакше нуль нічого не вартий.

Три винятки, і кожен із них — реальний патерн, а не відмазка:

1. **Click-away шар навколо оверлея.** Це той самий елемент, що центрує діалог,
   тому `aria-hidden` на ньому сховав би й діалог, а фокусованість поставила б
   безіменну зупинку перед кожним модальним вікном. Усе, що він робить, робить
   і кнопка закриття, і Escape.
2. **`onClick={e => e.stopPropagation()}`** — це не дія, а запобіжник, щоб клік
   усередині панелі не дійшов до шару під нею.
3. **Рядок, що передає клік контролу всередині себе**
   (`e.currentTarget.querySelector('button')?.click()`) — він лише розширює
   зону вказівника. Справжній контрол усередині: він кнопка, він у tab-порядку,
   і з клавіатури робить те саме.

Що змінилось у самому кіті, бо там виправлення розходиться на всі екрани:

- `FormGroup` тепер генерує `id` і зшиває підпис із контролом (`htmlFor`), а
  повідомлення про помилку — через `aria-describedby` і `aria-invalid`. До того
  кожне поле в продукті представлялось як безіменне текстове поле, а клік по
  підпису не фокусував нічого.
- `Checkbox` малює видиму «коробку» як `<label htmlFor>`, а не як `div` із
  обробником кліку поруч: перемикання стало нативним, разом із `disabled`.
- `Card` і `KpiCard` з `onClick` — це справжні `<button>`.
- Чекбокси всередині відрендереного markdown названі рядком, який перемикають.

Три помилки в самому чекері, які давали правдоподібне число замість падіння, і
через це закриті регресійними перевірками в `tests/kit-a11y.test.mjs`:

1. **«Компонент із великої літери — це текст».** `<button><ChevronRight/></button>`
   виглядав іменованим: 12 знахідок замість 30.
2. **`?.click()` — це `OptionalCallExpression`.** Перевірка на `CallExpression`
   проходила повз кожен рядок-форвардер у продукті.
3. **Роль на самому оверлеї, а не на дитині.** Лайтбокс — один елемент, і
   виняток його не бачив.

## Шари вирішують, а не специфічність

Іменовані розмірні контракти (`data-ui-composition`, `data-ui-padding`,
`data-ui-surface`) живуть у `globals.css` під `@layer components` і мають бути
тим самим «одним місцем», де написана геометрія композиції. **Половина того, що
вони оголошували, ніколи не доходила до екрана**, і ніщо про це не повідомляло.

Причина — шари каскаду, а не специфічність.
`.ui-control[data-ui-composition=…]` — це клас плюс атрибут, 0,2,0, і воно
легко перебиває `.px-4` з 0,1,0. Але Tailwind випускає
`@layer theme, base, components, utilities;`, а **порядок шарів виграє в
специфічності**: будь-яка утиліта з останнього шару б'є будь-яке правило з
попереднього. Щойно `Button` пише `px-4` у власному списку класів, кожен
`padding`, який композиція оголошує для нього, мертвий — тихо, з правилом, що
й далі лежить у файлі й виглядає як джерело істини.

Виняток — кастомні властивості. Саме тому `--ui-control-height` єдина частина
цих пресетів, яка завжди працювала: жодна утиліта її не ставить.

Нуль перебитих оголошень тримає **браузер**, а не скрипт:
`tests/visual/ui-kit.spec.mjs` бере перелік правил із
`layeredCompositionRules()` (це точно — просто розбір `globals.css`) і звіряє
кожну властивість із `getComputedStyle` на живому елементі в «Матриці
варіантів».

Спершу цей вердикт був статичним і за одну сесію помилився двічі — тому й
переїхав у браузер:

1. **Регулярка на лапках.** Апостроф у коментарі (`the component's own height`)
   відкривав «рядок», який ковтав усі списки класів після себе. Додавання JSDoc
   до `Button` прибрало з набору токенів усі його `bg-*` — звіт змінився без
   жодної зміни коду.
2. **Утиліта з варіантом чи з гілки — не те саме, що безумовна.**
   `hover:bg-canvas` не перебиває нічого в спокої, `bg-red-50` — лише поле в
   помилці. Обидві рахувались, і винуватцем називалась не та утиліта, що
   насправді виграє.

У `getComputedStyle` немає жодної з цих проблем: він повідомляє те, що браузер
розв'язав.

До того, як це почали міряти, перебитих оголошень було **50 у 20 правилах** —
включно з тим, що:

- `dialog-tabs` доставляв рівно одне: `flex: 1`. Gap, padding, radius, height і
  font-weight перебивав сам `Segmented`.
- `metric-editor`, `metric-text`, `project-name`, `status-entry` оголошували
  padding, font-size, font-weight, фон і колір рамки — жодне не застосовувалось.
- Чотири `duration-*` пресети резервували місце під підпис одиниці. `Input`
  давно робить це пропом `suffix`, який пише відступ інлайновим стилем — а він
  б'є будь-який шар. Правила лишались від старішого механізму.
- Три `*-transcript` пресети доставляли лише `line-height`.

Мертві оголошення видалені. Це не зсунуло нічого, крім одного місця: CI
перезняв усі тодішні секції і жоден бейзлайн не змінився, окрім двох нових. Селектори
лишились навіть там, де не лишилось жодного оголошення: маніфест варіантів
читає саме їх, і зникла композиція стала б «оголошеним значенням, якого немає»
у кожному виклику, що її передає.

Один виняток — і його варто знати, бо він показує межу знімкового тесту.
`inline-add-action` (QUI-137) просив стандартний сірий фон і чорнильний текст,
оголошував їх тут і віддавав прозорий фон із `#9a9a9a` текстом: обидві
властивості перебивали утиліти `Button`. Виміряно на старому коміті —
`background: rgba(0,0,0,0)`, `color: rgb(154,154,154)`. Колір тепер приходить
із `style="secondary"`, тобто звідти, де кіт і так тримає колір. Знімок цієї
зміни **не помітив**: три маленькі кнопки не набирають
`maxDiffPixelRatio: 0.001` на секції висотою 2164px. Пікселі ловлять зсув
верстки, а не тонкий колірний дрейф — саме тому computed-стилі міряються
окремо.

### Відступ їде так само, як висота

Два мертвих оголошення позначали не сміття, а реальний дефект: `invite-field`
резервував 150px під інлайнову кнопку «Запросити», `inline-edit` — 54px під
трейлінг-контрол, і поле не отримувало ні тих, ні тих.

Тепер горизонтальний відступ контролу їде тим самим механізмом, що й висота —
кастомною властивістю, якої утиліта поставити не може:

```css
.ui-control {
  padding-left:  var(--ui-control-pl, var(--ui-control-px, 0px));
  padding-right: var(--ui-control-pr, var(--ui-control-px, 0px));
}
.ui-button { --ui-control-px: 18px; }              /* md 16px, sm 12px */
.ui-field  { --ui-control-px: 12px; }              /* з іконкою — pl 36px */
```

`Button.SIZES` більше не містить `px-*`, `Input` — ні `pl-[12px]`, ні
`pr-[12px]`. Іконкові розміри лишають `p-0` утилітою навмисно: у квадрата немає
відступу, який комусь віддавати. Проп `suffix` теж не змінився — він пише
`paddingRight` інлайновим стилем, а інлайн б'є будь-який шар.

Виміряно на всіх 384 контролах `/ui-kit` до і після: **380 однакові**,
змінилися рівно чотири клітинки — `invite-field` і `inline-edit` на `Button` і
на `Input`, тобто ті два дефекти й нічого більше.

## Нативні контроли й локальні поверхні

`kit:audit` знаходить інтерактивні елементи та поверхні, намальовані повз кіт.
Єдине актуальне джерело їхньої кількості й розташування —
`fidelity-audit.generated.json`; ручні підсумки в документації застарівають і не
ведуться.

Повторюваний visual pattern переноситься в shared UI або отримує іменований
component preset. Справжній одноразовий виняток позначається точним
`data-ui-control` чи `data-ui-surface="local"`, щоб він залишався видимим у
звіті, але не видавався за універсальний компонент.

Затверджені межі лишаються такими:

- **AuthLayout** — Login і Onboarding поза зоною змін authenticated UI Kit.
- **UserStatusDialog** — його product usage є доказом оголошених status-варіантів;
  див. розділ нижче.
- **MobileNav і WorkspaceSidebar** — branded controls можуть читати `--sb-*`
  змінні теми й не зобов'язані набувати нейтрального вигляду `IconAction`.

Інші записи generated-звіту не вважаються схваленими лише тому, що вони вже
існують: новий повтор canonicalize, а новий виняток отримує явне пояснення.

## Що можна переносити в кіт, а що ні

Обхід продукту зупиняється на межі кіту (`workspace-ui-files.mjs` виключає
`src/components/ui`), і на цьому тримається метод «поверхонь»: компонент, який
несе свої класи дослівно, зникає зі звіту нативних контролів без зміни жодного
рядка класів. Але та сама межа має два наслідки, які легко проґавити.

**Розумний компонент у кіт не переносять.** `WorkspaceHeader` тягне
`AppContext`, стор, роутер і підписку на Firestore. Перенести його — це не
підвищення, а спосіб сховати від звіту: кіт отримав би компонент, який не
рендериться ні в каталозі, ні в тесті. Переносять розмітку — `UserMenu`,
`NotificationBell`, `NotificationCard` виїхали саме так, а стан лишився в
хедері.

**Компонент, чий виклик — єдиний доказ варіанта, лишається на місці.** Разом із
файлом зі звіту зникає і його вживання варіантів. `UserStatusDialog` — живий
приклад: він єдиний, хто вживає `Input composition="status-entry"`,
`Button composition="status-submit"` і `Dialog size="status"`. Після переїзду
всі три потрапили б у `declaredUnused`, поки продукт малює їх щоразу, коли
хтось ставить статус. Тому `tests/kit-drift.test.mjs` тримає стелю
`declaredUnused` — вона може лише падати.

## Дві таблиці — це не дубль

Правило «не заводь локальний компонент, схожий на наявний» одного разу вимагає
явного винятку, і ось він: `DataDisplay/DataTable` і
`TaskManagement/TaskTableView` — обидва таблиці, і обидва лишаються.

`DataTable` — таблиця цифр аналітики: презентаційна, рядок є посиланням, числа
праворуч, і **нижче брейкпоінта вона розсипається у стос карток**, бо шість
колонок чисел на телефоні не читаються. `TaskTableView` потребує майже всього
навпаки: примерзлий заголовок, примерзла колонка ідентичності, горизонтальна
прокрутка замість згортання в картки, контрол у клітинці, вибір рядків,
сортування по колонці й смуги груп. Спільний у них тег `<table>` і більш нічого;
злиття дало б один компонент із двома режимами без спільної середини, і кожна
зміна в аналітиці ризикувала б беклогом.

Всередині `TaskTableView` діє власне рішення того самого роду. Клітинка малює
значення звичайною розміткою і монтує справжній kit-контрол (`Select`,
`MultiSelect`, `DatePicker`, `Input`) лише коли її відкрили — **рівно один за
раз**. `Select`, залишений змонтованим у кожній клітинці, вішає по одному
`document.addEventListener('mousedown')` на клітинку: на беклозі в 200 рядків це
кілька сотень слухачів на кожен клік у сторінці. Клік, яким клітинку відкрили,
перенаправляється всередину щойно змонтованого контрола, тому «клік по клітинці
змінює значення» лишається одним кліком, а не двома.

## Невживаних компонентів не буває

Правило покриття забороняє показувати в каталозі компонент, якого продукт не
вживає — інакше showcase-only компонент зараховувався б як живий UI. Наслідок
виявився зворотним до задуманого: про такий компонент не можна було дізнатися
інакше, ніж прочитавши директорію, і кожні кілька місяців щось із них писали
заново. Так набралось 31 — більше третини кіту, і половина з них дублювала щось
уже живе (`Avatar` поруч із `UserAvatar`, `Badge` поруч із `Pill`, `Chip` поруч
із `Tag`, `Stat` поруч із `KpiCard`).

Вони видалені. **Невживаний тепер означає видалений**, і `npm run test:unit`
падає, поки в `src/components/ui` лежить щось недосяжне. Код лишається в git.

Три речі, які «недосяжний» не означає:

1. **Досяжний через інший компонент кіту.** `TopHeader` рендерить `Breadcrumb` і
   `HeaderSearch` на кожному екрані. Обхід продукту зупиняється на межі кіту, тож
   обидва показували нуль використань — і перший прохід чистки їх видалив.
   Тепер це поле `usedByKit`; власного preview такий компонент не винен, його
   показує хост.
2. **Імпортований під іншим іменем.** `import UiToast from '…/Feedback/Toast'` —
   default export не має власного імені, тому іменем є файл. `Toast` місяцями
   рахувався невживаним, хоча висить на кожному екрані.
3. **Файл, що лише перейменовує інший компонент** (`export default IssueCard`) —
   не компонент і в інвентар не потрапляє взагалі.

## Джерело істини і пропагація

Каталог `/ui-kit` — дзеркало, а не джерело. Зміна в ньому нічого не поширює.
Поширюють два рівні, і тільки вони:

1. `src/app/globals.css` — `@theme` токени, `--ui-*` semantic contract і
   `data-ui-*` правила (геометрія, типографіка, composition-пресети).
2. `src/components/ui/*` — самі компоненти та їхні lookup-мапи
   (`Button.ICON_SIZES`, `UserAvatar.AVATAR_SIZES`, `Surface.PRESETS`…).

Правило: **значення живе в одному з цих двох рівнів, ніколи на місці виклику.**
Вільний проп (`iconSize={16}`, `size={28}`) робить пропагацію неможливою — кожен
виклик тримає власну копію рішення. Такі пропси прибрані й не повертаються:
розмір іконки виводиться з `size`, розмір аватара — з іменованого токена.

Композиція (`flex-1`, `h-full`, зовнішні margin) на місці виклику дозволена: вона
розміщує компонент у батьку й нічого не перевизначає. Заборонено інше — власна
висота, padding, radius чи typography поверх компонента.

## Бюджет різноманіття

Каталог — канон. Варіант існує тоді, коли його вживають **щонайменше три рази**;
інакше це хардкод під іменем варіанта, і його зливають у найближчий канонічний.

Наслідок першого проходу: `Pill.size` 14 → 4 (`sm`/`md`/`lg`/`wide-sm`),
`IconAction.appearance` 16 → 11, `IconAction.size` 8 → 7, `Dialog.size` 6 → 4,
`Counter` numeric 4 → 3, `Card.preset` 3 → 2, `Button` icon-боксів 7 → 6.
Найбільші дублікати були буквальні: `Pill sm`/`compact-md` мали однакову
геометрію й різнились 1px шрифту, `IconAction pane`/`editor` — байт-у-байт
однакові класи, `neutral-hover` (#f5f5f5) проти `neutral` (#f4f4f5).

Правило має три винятки, і вони не «менше трьох використань, але шкода
видаляти» — вони про призначення:

1. **Семантичні тони** (`danger`, `dark`, `info`, `success`, `warning`) несуть
   значення, а не геометрію. Злити їх — не прибрати дублікат, а втратити сенс.
2. **Окремі кольори з роллю**: `accent`, `overlay`, `inverse-outline`,
   `auth-close` — інший контраст для темних чи накладених поверхонь.
3. **Найменший розмір, коли він функціональний**: `Counter size="xs"` (12px)
   тримає числовий бейдж на іконці дзвінка; `sm` (16px) там переллється.

Перед тим як додати новий варіант, перевір панель «Де використовується» на
preview компонента: рідкісні варіанти позначені жовтим саме для цього.

## Маніфест варіантів

`scripts/kit-variants.mjs` виводить перелік варіантів **із реалізації**: з
lookup-мап компонентів і з `data-ui-*` селекторів у `globals.css`. Рукописного
списку немає навмисно — перша спроба була рукописною і помилилась одразу
(пропустила `Pill tone="ink-subtle"`, `size="thin-md"`, чотири Button-composition
і два розміри Dialog). Це та сама хвороба, що й рукописні preview, лише рівнем
вище.

`/ui-kit` → «Матриця варіантів» рендерить кожне оголошене значення. Тому
«варіант існує, але його немає в каталозі» більше неможливий стан: щоб додати
варіант, треба додати запис у мапу або правило в CSS — і він з'явиться сам.
Компоненти, які не рендеряться окремо (Dialog, PageHeader, FilterBar…),
показують оголошені значення з явною причиною замість вигаданого прикладу.

`npm run kit:drift` тримає три нулі:

- значень, яких маніфест не оголошує — 0;
- пропів поза маніфестом — 0;
- `className`, що перевизначає компонент — 0.

`npm run test:unit` падає, якщо будь-який перестає бути нулем.

## Відкриті розбіжності

`kit:audit` питає, чи продукт узагалі бере компонент із кіту. `kit:drift` питає
інше: якщо бере — чи виглядає воно так, як показує preview. Компонент може бути
імпортований усюди, мати зелене покриття і все одно рендеритись на екрані
інакше, ніж у власному preview.

Три категорії — контрактні нулі, і `npm run test:unit` падає, щойно якась
перестає бути нулем:

| Категорія | Що означає |
| --- | --- |
| `undeclaredValues` | Значення варіанта, якого реалізація не оголошує. Компонент тихо падає на default. |
| `unknownProps` | Проп із набором варіантів, якого маніфест не знає для цього компонента. |
| `chromeOverrides` | `className`, що перевизначає геометрію чи типографіку компонента. |

Розміщення в батьківському контейнері (`flex-1`, `h-full`, `min-h-0`, зовнішні
margin) — легітимна композиція і не рахується.

Четверта, `usedWithoutPreview`, теж нуль: **кожен варіант, який сайт показує,
видно в каталозі**. Починалось із 53 — тобто «кіт є джерелом» було правдою про
компонент і брехнею про половину його варіантів.

Закрито структурно, а не вручну. `/ui-kit` → «Матриця варіантів» рендерить по
одному живому прикладу на кожне оголошене значення, беручи їх із того самого
маніфесту, що й сам варіант. Тому варіант **не може** існувати без preview:
додав запис у мапу або правило в CSS — приклад з'явився сам.

Компонент, який не стоїть окремо (`Dialog` потребує відкритого стану,
`PageHeader` — цілої сторінки), не вигадує собі приклад: він у `VARIANT_ELSEWHERE`
із причиною й вказівкою на розділ, де його значення показані по-справжньому.

Правило для нової UI-роботи: не додавати черговий override поверх
shared-компонента, а закрити відповідний рядок звіту.
